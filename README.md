# GymRat MCP 🏋️

> **카카오톡에서 "나를 기억하는" AI 퍼스널 트레이너.**
> 프로필·운동·식단·인바디를 시계열로 누적하고, 그 기록을 다시 **처방에 먹여** 점진적 과부하·자동 디로드·부상 회피까지 자동으로 반영하는 [MCP(Model Context Protocol)](https://modelcontextprotocol.io) 서버입니다.

카카오톡 Play MCP 채팅창에 자연어로 말을 걸면, 호스트 LLM이 이 서버의 툴을 호출해 **결정론적 룰 기반**으로 운동·식단을 코칭합니다. "일반 챗봇과 뭐가 다른가?"에 대한 답은 **기록의 누적과 그 기록이 다음 처방을 바꾼다는 피드백 루프**입니다.

## 무엇을 만들었나

카카오톡 하나로 돌아가는 개인 PT 봇입니다. 사용자는 앱 설치 없이 채팅으로:

- **프로필을 심고** — 목표(증량/감량/유지)·경력·부상·페르소나를 기억시킴
- **기록하고** — "벤치 70 5x5, 인클 60 3x10 했어" 같은 자연어 운동 기록, 체중·인바디 수치, 식단 텍스트
- **분석받고** — 체중·볼륨·인바디·식단의 시계열 추세
- **처방받는다** — 목표·이력·부상·최근 볼륨 흐름을 종합한 오늘의 루틴과 식단 가이드

핵심 차별점은 **"매 세션 나를 기억함"**과 **"기록이 다음 처방을 실제로 바꾼다"**입니다. 예를 들어 벤치 80kg 8회를 다 채워 기록하면, 다음 가슴 루틴의 벤치 처방 무게가 자동으로 82.5kg으로 오릅니다(점진적 과부하). 반대로 최근 볼륨이 정체되면 시스템이 스스로 **회복 주간(디로드)**을 잡아 세트·무게를 낮춥니다.

## 왜 이렇게 설계했나 (핵심 의사결정)

포트폴리오로서 봐주셨으면 하는 부분은 기능 목록이 아니라 **아래의 트레이드오프 판단들**입니다.

### 1. 코칭 로직은 LLM이 아니라 결정론적 룰로
운동 처방·볼륨 계산·무게 증분은 전부 순수 Python 룰 엔진입니다(`tools/` 내부, LLM 호출 0). **왜?**
- **재현 가능성** — "벤치 80 → 82.5"가 매번 정확히 같아야 신뢰가 생김. LLM 환각으로 무게가 널뛰면 안 됨.
- **테스트 가능성** — 처방은 순수 함수라 73개 유닛 테스트로 수치까지 못 박아 검증.
- **역할 분리** — LLM(호스트)은 **말투와 자연어 파싱**만, 서버는 **로직과 안전**만 담당.

### 2. 안전 가드레일을 페르소나보다 위에
"천사/악마/코치/현실파이터" 4종 페르소나는 **말투(tone)만** 바꿉니다. 어떤 페르소나에서도:
- 정확한 kcal/그램 수치 처방 ❌ → 질적 균형 가이드만
- 하드한 제한식·굶기·식이강박 조장 ❌
- 몸 모욕·죄책감 유발 ❌

이 가드레일은 코드 레벨에서 항상 주입되고(`persona.build_persona_context`), 테스트로 강제됩니다. 건강 도메인에서 "재미"가 안전을 넘지 못하게 하는 게 설계 원칙이었습니다.

### 3. 영↔한 종목 브리지 — 데이터 단절을 잇는 얇은 매핑
운동 라이브러리는 영문 1,324종(`barbell bench press`), 사용자 로그는 한글 별칭(`벤치`, `벤치프레스`)입니다. 이 둘이 안 맞으면 점진적 과부하가 **영영 발화하지 않는** 치명적 단절이 있었습니다.

해결책으로 사람이 실제로 로그하는 **28종만 손수 큐레이션해 대표 영문명 1개로 매핑**하고, 나머지 긴 꼬리(1,296종)는 의도적으로 무시했습니다(`tools/exercise_map.py`). 매핑 안 된 종목은 그냥 첫 처방으로 폴백(회귀 없음). **완벽한 자동 매핑 대신 커버리지 검증이 가능한 명시적 매핑**을 택한 판단입니다(`tests/test_exercise_map.py`가 28종이 전부 실재하는지 검증).

### 4. "빈 루틴은 절대 반환하지 않는다"는 불변식
호스트 LLM이 `focus="lower body"`(영문)나 `"asdf"`(오타)를 보내도, 부상으로 종목이 대량 제외돼도, 신규 유저라 기록이 0건이어도 — **항상 유효한 루틴이 나가야** 합니다. 부상/최근 자극 부위는 "제외"가 아니라 "후순위로 미룸", 미인식 focus는 일수 기반 분할로 폴백. 사용자 입장에서 "빈 화면"만큼 나쁜 UX가 없다는 원칙입니다.

### 5. MCP를 고른 이유
카카오톡 Play MCP를 프론트로 쓰면 **앱/서버 프론트엔드 없이** 이미 수천만이 쓰는 메신저가 UI가 됩니다. 능동 푸시가 불가능한 제약은 **톡캘린더 이벤트 생성**으로 우회했습니다(식단 리마인드).

## 코칭 루프: 기록 → 분석 → 처방

이 프로젝트의 정체성인 **피드백 루프**를 단계별로 뜯어보면:

### 1) 기록 (`log_workout`, `log_weight`, `log_inbody`, `log_meal`)
- 자연어 파서가 `"벤치 70 5x5"` → `{exercise: "벤치프레스", weight: 70, sets: 5, reps: 5}`로 구조화
- `NxN`, 한글 단위(`3세트 10회`), 별칭/영문(`사레레`, `deadlift`)까지 정규화
- 무게 누락 시 **직전 동일 종목 기록에서 자동 채움**(`confirm_with_history`)

### 2) 분석 (`analyze_trend`)
- **볼륨 추세**: 세션별 총 볼륨(무게×세트×반복)을 초반 절반 vs 후반 절반 평균으로 비교
- 맨몸 컴파운드(풀업/딥스)는 무게가 없어 볼륨 0으로 빠지는 문제를 **체중 프록시**로 보정 → "거짓 하락" 방지
- 체중·인바디·식단도 각각 방향성(up/down/flat) + 질적 요약. **정확 수치 단정은 하지 않음**

### 3) 처방 (`generate_routine`) — 분석 결과를 먹는다
`generate_routine` 한 번의 호출이 아래를 **한꺼번에** 반영합니다:

| 기능 | 동작 |
|---|---|
| **점진적 과부하** | 영↔한 브리지로 직전 기록을 찾아 무게 자동 증분 (상체 +2.5kg / 하체 +5kg) |
| **더블 프로그레션** | 목표 렙 달성 → 무게↑ / 미달 → 무게 유지 + 렙 +1 |
| **자동 디로드** | 볼륨 하락·정체 감지 **또는** 주기화 N주차 → 세트 −1, 무게 ×0.9 |
| **주기화 프로그램** | 유저별 활성 블록의 "주차"를 시작일 기준 결정론적으로 파생, 4주마다 디로드 |
| **부상 회피** | "회전근개" → 오버헤드 프레스류 제외, 안전 종목(사이드 레이즈)은 유지 |
| **회복/빈도 인지** | 최근 48h 자극 부위는 후순위, 주간 부위별 볼륨이 10세트 미만이면 보완 안내 |
| **패턴 균형** | 하루 처방을 밀기/당기기/힌지/스쿼트/코어로 분산 ("가슴 6종 수프" 방지) |
| **컴파운드 우선** | 다관절·정석 장비(바벨>덤벨>머신) 우선, 올림픽 리프트는 후순위 |

> **"벤치 80kg 8회 완수" 로그 한 줄이 → 볼륨 추세에 반영되고 → 다음 가슴 루틴의 벤치 처방을 82.5kg으로 올린다.** 이 한 문장이 프로젝트 전체의 요약입니다.

## MCP 툴 목록

| 툴 | 설명 |
|---|---|
| `get_profile` / `update_profile` | 목표·경력·부상·페르소나 조회/부분 갱신 (영문·변형 입력도 한글 정규화) |
| `log_weight` | 체중(kg)·체지방률 기록 |
| `log_inbody` | 인바디 수치 저장 + 프로필 요약 갱신 + 직전 대비 변화 코멘트 |
| `log_workout` | 자연어 운동 기록 파싱·저장, 무게 자동 채움 |
| `log_meal` | 식단 텍스트 저장 + 질적 균형 코멘트 (수치 처방 ❌) |
| `analyze_trend` | 체중/볼륨/인바디/식단 시계열 추세 분석 |
| `generate_routine` | 목표·이력·부상·추세 종합 루틴 처방 (위 코칭 루프의 종착점) |
| `generate_meal_plan` | 끼니별 질적 식단 가이드 + 톡캘린더 알림 이벤트 |
| `get_recommendation` | 체중·인바디·식단 추세를 묶은 종합 코칭 한마디 |

## 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| MCP 서버 | **FastMCP 2.x** | 데코레이터로 툴 등록, Streamable HTTP 전송(원격 엔드포인트 등록용) |
| ORM / DB | **SQLAlchemy 2.x** / SQLite(dev) · **PostgreSQL**(prod) | `DATABASE_URL` 하나로 dev↔prod 전환, 스키마 코드 공유 |
| 런타임 | **Python 3.12** | |
| 컨테이너 | **Docker Compose** | 서버 + Postgres + Caddy 3-티어 |
| 리버스 프록시 | **Caddy 2** | 도메인만 넣으면 Let's Encrypt HTTPS 자동 발급 |
| 배포 | **AWS Lightsail** + **GitHub Actions** | `dev` 머지 시 테스트 게이트 통과 후 SSH 자동 배포 |
| 테스트 | **pytest** (73 케이스) | 결정론적 룰이라 수치까지 단언 |

## 로컬 실행

```bash
# 1) 가상환경 & 의존성
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 2) 운동 라이브러리 시드 (최초 1회 — dev DB에 1,324종 적재)
python -m db.seed_exercises

# 3) 서버 기동 (Streamable HTTP, 기본 :8000)
python server.py
```

> 서버는 기동 시 테이블을 자동 생성하고(`init_db`), 라이브러리가 비어 있으면 자동 시드합니다.
> DB는 기본 `sqlite:///./gymrat_dev.db`, `DATABASE_URL` 환경변수로 Postgres 등으로 교체합니다.

## 테스트

```bash
pytest -q
```

73개 유닛 테스트가 다음을 커버합니다:

- **처방 수치 검증** — 점진적 과부하(+2.5/+5), 더블 프로그레션, 디로드(-1세트/×0.9)
- **영↔한 브리지 커버리지** — 큐레이션 28종이 전부 라이브러리에 실재하는지
- **파서 정확도** — NxN·한글 단위·별칭·누락 감지
- **추세 분석** — insufficient_data 방어, 맨몸 볼륨 프록시
- **가드레일** — 페르소나가 안전 규칙을 못 넘는지 (persona harness)
- **주기화** — 주차 파생·자동 디로드 타이밍

추가로 [`docs/kakao-test-scenarios.md`](docs/kakao-test-scenarios.md)에 **카카오톡 채팅창에 직접 쳐 보는 21개 섹션 실사용 E2E 대본**(💬입력 / 🔧호출 툴 / ✅합격 기준)이 있습니다.

## 배포

`docker-compose.prod.yml`이 **서버 + Postgres + Caddy** 3-티어를 올립니다.

```bash
DOMAIN=your.domain POSTGRES_PASSWORD=... docker compose -f docker-compose.prod.yml up -d --build
```

- **Caddy**가 443만 외부 노출, 인증서 자동 발급
- **GitHub Actions**(`.github/workflows/deploy.yml`)가 `dev` 브랜치 머지 시 `pytest` 통과를 게이트로 Lightsail에 SSH 배포
- PR은 테스트만 실행(배포 X)
