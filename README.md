# GymRat MCP 🏋️

> **카카오톡에서 "나를 기억하는" AI 퍼스널 트레이너.**
> 프로필·운동·식단·인바디를 시계열로 누적하고, 그 기록을 다시 **처방에 먹여** 점진적 과부하·자동 디로드·부상 회피·개인 분할까지 자동으로 반영하는 [MCP(Model Context Protocol)](https://modelcontextprotocol.io) 서버입니다.

카카오톡 Play MCP 채팅창에 자연어로 말을 걸면, 호스트 LLM이 이 서버의 툴을 호출해 **결정론적 룰 기반**으로 운동·식단을 코칭합니다. "일반 챗봇과 뭐가 다른가?"에 대한 답은 **기록의 누적과 그 기록이 다음 처방을 바꾼다는 피드백 루프**입니다.

> 모든 입력은 **텍스트**입니다. 사진·이미지 업로드에 의존하지 않고, 운동·식단·인바디 수치까지 전부 대화로 주고받습니다.

## 무엇을 만들었나

카카오톡 하나로 돌아가는 개인 PT 봇입니다. 사용자는 앱 설치 없이 채팅으로:

- **프로필을 심고** — 목표(증량/감량/유지)·경력·부상·보유 장비·운동일수·분할 스타일·페르소나를 기억시킴
- **기록하고** — "벤치 70 5x5, 인클 60 3x10 했어" 같은 자연어 운동 기록, 체중·인바디 수치, 식단 텍스트. "3주 전 벤치 70"처럼 **지난 기록을 나중에 채워 넣거나**, 잘못 적은 건 **대화로 바로 수정·삭제**
- **분석받고** — 체중·볼륨·인바디·식단 추세 + 종목별 **추정 1RM(e1RM) 추이**, **주간 리캡**(부위별 볼륨/부족 부위), **목표 도달 예상일 투영**
- **처방받는다** — 목표·이력·부상·최근 볼륨·개인 분할을 종합한 오늘의 루틴(무게·세트·반복·휴식·강도·자세 큐)과 근거 기반 식단 가이드

핵심 차별점은 **"매 세션 나를 기억함"**과 **"기록이 다음 처방을 실제로 바꾼다"**입니다. 예를 들어 벤치 80kg 8회를 다 채워 기록하면, **신기록(PR)을 자동 감지해 축하**하고 다음 가슴 루틴의 벤치 처방 무게가 자동으로 82.5kg으로 오릅니다(점진적 과부하). 반대로 최근 볼륨이 정체되면 시스템이 스스로 **회복 주간(디로드)**을 잡아 세트·무게를 낮춥니다.

그리고 **사람마다 다른 분할**을 반영합니다 — 초보는 PPL·상하체·부위별 **프리셋**을 경력에 맞게 추천받고, 중급 이상은 **자기 분할을 day별로 직접 정의·수정**할 수 있습니다. "오늘 뭐 하지?"는 로그 개수가 아니라 **가장 오래 안 한 부위(recency)**로 골라, 하루 한 부위면 그 부위 종목이 충분히 나오도록 배분합니다.

## 왜 이렇게 설계했나 (핵심 의사결정)

포트폴리오로서 봐주셨으면 하는 부분은 기능 목록이 아니라 **아래의 트레이드오프 판단들**입니다.

### 1. 코칭 로직은 LLM이 아니라 결정론적 룰로
운동 처방·볼륨 계산·무게 증분은 전부 순수 Python 룰 엔진입니다(`tools/` 내부, **서버 아웃바운드 LLM 호출 0**). **왜?**
- **재현 가능성** — "벤치 80 → 82.5"가 매번 정확히 같아야 신뢰가 생김. LLM 환각으로 무게가 널뛰면 안 됨.
- **테스트 가능성** — 처방은 순수 함수라 200+ 유닛 테스트로 수치까지 못 박아 검증.
- **역할 분리** — LLM(호스트)은 **말투와 자연어 파싱**만, 서버는 **로직과 안전**만 담당.

### 2. 안전 가드레일을 페르소나보다 위에
"천사/악마/코치/현실파이터" 4종 페르소나는 **말투(tone)만** 바꿉니다. 어떤 페르소나에서도:
- 정확한 kcal/그램 수치 처방 ❌ → 질적 균형 가이드만
- 하드한 제한식·굶기·식이강박 조장 ❌
- 몸 모욕·죄책감 유발 ❌

이 가드레일은 코드 레벨에서 항상 주입되고(`persona.build_persona_context`), 테스트로 강제됩니다. 건강 도메인에서 "재미"가 안전을 넘지 못하게 하는 게 설계 원칙이었습니다.

### 3. 영↔한 종목 브리지 — 데이터 단절을 잇는 얇은 매핑
운동 라이브러리는 영문 1,324종(`barbell bench press`), 사용자 로그는 한글 별칭(`벤치`, `벤치프레스`)입니다. 이 둘이 안 맞으면 점진적 과부하가 **영영 발화하지 않는** 치명적 단절이 있었습니다.

해결책으로 사람이 실제로 로그하는 **28종만 손수 큐레이션해 대표 영문명 1개로 매핑**하고, 나머지 긴 꼬리(1,296종)는 의도적으로 무시했습니다(`tools/exercise_map.py`). 매핑 안 된 종목은 그냥 첫 처방으로 폴백(회귀 없음). **완벽한 자동 매핑 대신 커버리지 검증이 가능한 명시적 매핑**을 택한 판단입니다(`tests/test_exercise_map.py`가 28종이 전부 실재하는지 검증).

### 4. "빈 루틴은 절대 반환하지 않는다"는 불변식
호스트 LLM이 `focus="lower body"`(영문)나 `"asdf"`(오타)를 보내도, 부상으로 종목이 대량 제외돼도, 신규 유저라 기록이 0건이어도 — **항상 유효한 루틴이 나가야** 합니다. 부상/최근 자극 부위는 "제외"가 아니라 "후순위로 미룸", 미인식 focus는 분할·일수 기반으로 폴백. 사용자 입장에서 "빈 화면"만큼 나쁜 UX가 없다는 원칙입니다.

### 5. 분할은 프리셋이 아니라 "그 사람의 분할"
초보에겐 검증된 프리셋(PPL/상하체/부위별)을 경력 기반으로 권하되, 중급 이상은 자기 분할을 강제받지 않습니다. `set_workout_split`으로 day별 부위 구성을 직접 저장하고, "오늘의 날"은 **recency**(가장 오래 안 한 부위)로 결정합니다. 부위 수에 따라 종목 수를 배분해(1부위면 5종, 2부위면 3+2 …) "가슴날인데 2종만" 같은 빈약한 처방을 막습니다.

### 6. 식단은 근거 있는 정성 코칭 — 텍스트로만
식단 카탈로그(`meal_db/`)는 정확 칼로리·그램이 아니라 **정성적 플레이트 구성**과 **근거 출처**(ACSM·ISSN·USDA 등)를 담습니다. 사용자는 사진 없이 **텍스트로 식단을 말하면** 질적 균형 코멘트를 받고, 끼니별 가이드는 같은 계획 안에서 메뉴·재료 반복을 줄여 다양하게 제안합니다. 수치 강요·식이강박을 구조적으로 배제한 선택입니다.

### 7. MCP를 고른 이유
카카오톡 Play MCP를 프론트로 쓰면 **앱/서버 프론트엔드 없이** 이미 수천만이 쓰는 메신저가 UI가 됩니다. 능동 푸시가 불가능한 제약은 **톡캘린더 이벤트 생성**으로 우회했습니다(식단 리마인드).

**책임 분리가 핵심입니다.** 호스트 LLM은 "언어"를, 서버는 "로직과 데이터와 안전"을 맡습니다. `server.py`는 툴 등록만 하는 얇은 진입점이고 모든 로직은 `tools/`에 있습니다. 운동/프로필 데이터는 메인 DB, 근거 기반 식단 카탈로그는 격리된 `meal_db/`로 분리했습니다.

## 코칭 루프: 기록 → 분석 → 처방

이 프로젝트의 정체성인 **피드백 루프**를 단계별로 뜯어보면:

### 1) 기록 (`log_workout`, `log_weight`, `log_inbody`, `log_meal`)
- 자연어 파서가 `"벤치 70 5x5"` → `{exercise: "벤치프레스", weight: 70, sets: 5, reps: 5}`로 구조화
- `NxN`, 한글 단위(`3세트 10회`), 별칭/영문(`사레레`, `deadlift`)까지 정규화
- 무게 누락 시 **직전 동일 종목 기록에서 자동 채움**(`confirm_with_history`)
- 세트를 `ExerciseSet` 테이블에 단위로 저장 → 종목별 e1RM/PR 계산의 기반
- **PR 자동 감지** — 저장 시 이전 최고 e1RM과 비교해 신기록이면 축하 헤드라인
- **상대 날짜 백필**("3주 전 …")과 **수정·삭제**(`edit_workout`/`delete_workout`)로 과거 기록 정정

### 2) 분석 (`analyze_trend`, `get_exercise_history`, `get_weekly_recap`, `get_goal_projection`)
- **볼륨 추세**: 세션별 총 볼륨(무게×세트×반복)을 초반 절반 vs 후반 절반 평균으로 비교
- 맨몸 컴파운드(풀업/딥스)는 무게가 없어 볼륨 0으로 빠지는 문제를 **체중 프록시**로 보정 → "거짓 하락" 방지
- **종목별 추정 1RM(e1RM) 시계열** — "내 벤치가 는다"를 숫자·추세로 표면화
- **주간 리캡** — 부위별 주간 세트량과 부족 부위를 짚음
- **목표 투영** — 현재 e1RM + 최근 상승률로 `"9월까지 벤치 100kg"` 도달 예상일 선형 투영(비현실적 목표엔 신중 모드)
- 체중·인바디·식단도 각각 방향성(up/down/flat) + 질적 요약. **정확 수치 단정은 하지 않음**

### 3) 처방 (`generate_routine`) — 분석 결과를 먹는다
`generate_routine` 한 번의 호출이 아래를 **한꺼번에** 반영합니다:

| 기능 | 동작 |
|---|---|
| **점진적 과부하** | 영↔한 브리지로 직전 기록을 찾아 무게 자동 증분 (상체 +2.5kg / 하체 +5kg) |
| **더블 프로그레션** | 목표 렙 달성 → 무게↑ / 미달 → 무게 유지 + 렙 +1 |
| **역할별 처방** | 종목 역할(컴파운드/고립)에 맞는 sets·reps·**휴식(rest_sec)**·**목표 강도(RPE)** — 스쿼트와 레터럴 레이즈가 같은 4×8이 되지 않게 |
| **자동 디로드** | 볼륨 하락·정체 감지 **또는** 주기화 N주차 → 세트 −1, 무게 ×0.9 |
| **주기화 프로그램** | 유저별 활성 블록의 "주차"를 시작일 기준 결정론적으로 파생, 4주마다 디로드 |
| **개인 분할** | PPL·상하체·부위별 프리셋 또는 유저 커스텀 분할, "오늘의 날"은 recency로 선택 |
| **부위별 종목 배분** | 하루 부위 수에 따라 종목 수 분배(1부위=5종, 2부위=3+2 …) — 빈약/과잉 방지 |
| **부상 회피** | "회전근개" → 오버헤드 프레스류 제외, 안전 종목(사이드 레이즈)은 유지 |
| **회복/빈도 인지** | 최근 48h 자극 부위는 후순위, 주간 부위별 볼륨이 10세트 미만이면 보완 안내 |
| **패턴 균형** | 하루 처방을 밀기/당기기/힌지/스쿼트/코어로 분산 ("가슴 6종 수프" 방지) |
| **컴파운드 우선** | 다관절·정석 장비(바벨>덤벨>머신) 우선, 올림픽 리프트는 후순위 |

> **"벤치 80kg 8회 완수" 로그 한 줄이 → PR로 축하받고 → 볼륨 추세·e1RM에 반영되고 → 다음 가슴 루틴의 벤치 처방을 82.5kg으로 올린다.** 이 한 문장이 프로젝트 전체의 요약입니다.

## MCP 툴 목록

**프로필 · 기록**

| 툴 | 설명 |
|---|---|
| `get_profile` / `update_profile` | 목표·경력·부상·장비·운동일수·분할 스타일·페르소나 조회/부분 갱신 (영문·변형 입력도 한글 정규화) |
| `log_weight` | 체중(kg)·체지방률 기록 |
| `log_inbody` | 사용자가 알려준 인바디 수치 저장 + 프로필 요약 갱신 + 직전 대비 변화 코멘트 |
| `log_workout` | 자연어 운동 기록 파싱·저장, 무게 자동 채움, 세트 단위 저장, PR 감지 |
| `edit_workout` / `delete_workout` | 잘못 적은 운동 기록 수정·삭제 |
| `get_recent_workouts` | 최근 운동 기록 조회 |
| `log_meal` / `confirm_meal_details` | 식단 텍스트 저장 + 질적 균형 코멘트 (수치 처방 ❌), 애매하면 확인 질문 |

| 툴 | 설명 |
|---|---|
| `analyze_trend` | 체중/볼륨/인바디/식단 시계열 추세 분석 |
| `get_exercise_history` | 종목별 추정 1RM(e1RM) 시계열 |
| `get_weekly_recap` | 주간 부위별 볼륨 + 부족 부위 리캡 |
| `get_goal_projection` | 목표 무게 도달 예상일 투영 |

**처방 · 분할 · 식단**

| 툴 | 설명 |
|---|---|
| `generate_routine` | 목표·이력·부상·추세·분할 종합 루틴 처방 (코칭 루프의 종착점) |
| `set_workout_split` / `get_workout_split` / `clear_workout_split` | 커스텀 분할 정의·조회·초기화(프리셋 복귀) |
| `generate_meal_plan` | 근거 기반 끼니별 질적 식단 가이드 + 톡캘린더 알림 이벤트 |
| `suggest_meal_adjustment` | 방금 먹은 식단에 대한 다음 끼니 보정 제안 |
| `get_recommendation` | 체중·인바디·식단 추세를 묶은 종합 코칭 한마디 |

> `reset_user_data`는 사용자가 "처음부터/초기화/리셋"을 명확히 요청했을 때 모든 기록·프로필을 지워 완전 초기 상태로 되돌립니다(되돌릴 수 없음).

## 기술 스택

## 로컬 실행

```bash
# 1) 가상환경 & 의존성
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 2) 운동 라이브러리 시드 (최초 1회 — dev DB에 1,324종 적재)
python -m db.seed_exercises

# 3) 서버 기동 (Streamable HTTP, 기본 :8000)
python server.py
```

> 서버는 기동 시 테이블을 자동 생성하고(`init_db`), 라이브러리가 비어 있으면 자동 시드합니다.
> DB는 기본 `sqlite:///./gymrat_dev.db`, `DATABASE_URL` 환경변수로 Postgres 등으로 교체합니다.

## 테스트

```bash
pytest -q
```

208개 유닛 테스트(22개 파일)가 다음을 커버합니다:

- **처방 수치 검증** — 점진적 과부하(+2.5/+5), 더블 프로그레션, 역할별 sets/reps/휴식, 디로드(-1세트/×0.9)
- **분할 개인화** — 프리셋/커스텀 분할, recency 기반 "오늘의 날", 부위별 종목 배분
- **영↔한 브리지 커버리지** — 큐레이션 28종이 전부 라이브러리에 실재하는지
- **PR·e1RM 추적** — 세트 단위 저장, 신기록 감지, 종목별 히스토리
- **파서 정확도** — NxN·한글 단위·별칭·누락 감지·상대 날짜 백필
- **추세/리캡/투영** — insufficient_data 방어, 맨몸 볼륨 프록시, 목표 투영 가드레일
- **식단** — 근거 기반 카탈로그, 텍스트 계약, 메뉴 다양성
- **가드레일** — 페르소나가 안전 규칙을 못 넘는지 (persona harness / 맥락 렌더링 / 입력 안전)
- **주기화** — 주차 파생·자동 디로드 타이밍

추가로 [`docs/kakao-test-scenarios.md`](docs/kakao-test-scenarios.md)에 **카카오톡 채팅창에 직접 쳐 보는 실사용 E2E 대본**(💬입력 / 🔧호출 툴 / ✅합격 기준)이 있습니다.

## 배포

`docker-compose.prod.yml`이 **서버 + Postgres + Caddy** 3-티어를 올립니다.

```bash
DOMAIN=your.domain POSTGRES_PASSWORD=... docker compose -f docker-compose.prod.yml up -d --build
```

- **Caddy**가 443만 외부 노출, 인증서 자동 발급
- **GitHub Actions**(`.github/workflows/deploy.yml`)가 `dev` 브랜치 머지 시 `pytest` 통과를 게이트로 Lightsail에 SSH 배포
- PR은 테스트만 실행(배포 X)
